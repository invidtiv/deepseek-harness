# Agent Note: Telegram forum topics are a native per-topic frontend

Status: implemented

English | [中文](2026-08-20-telegram-topic-frontend.zh.md)

## Problem

Telegram forum topics should each act as one durable agent session with its own working folder, without a parallel runtime, a sidecar, or changes to the harness core. The prior analysis (`telegram-topics-analysis.md`, produced inside this repository) established that every load-bearing primitive already exists and is per-session: the immutable validated `SessionHeader.cwd` threaded through every tool, restart-safe resume over the append-only session log, the ACP bridge as an external-transport template (`inject: ['agents']`, followup + `session/event` + `whenIdle`), durable domain-KV storage, and the workspace registry's canonical-path validation. The question was whether a Telegram frontend fits the existing extension points, and what the new code surface is.

## Decision

Telegram ships as one plugin package, one patch-only bundle, and one example leaf. No core, loop, session-format, or existing-bundle change exists in the change.

- **`@deepseek-ai/dsh-telegram`** (`packages/telegram/telegram`) is a function plugin declaring `inject: ['agents']` only; it mounts its runtime in a child fiber requiring `storageDomain`, `credentials`, and `sessionPersistence` (the storage-domain activation pattern), with `attachments`, `commands`, `userQuestions`, `workspaceRegistry`, and the approval event read optionally via `ctx.get()`. The topic→session mapping is the plugin's own storage-domain unit named `telegram_topics` (the storage `UNIT_NAME_RE` forbids hyphens, so the analysis's proposed `telegram-topics` name is not a legal domain name), with one `topics` table plus one `history` table for `/reset` audit rows. Session ids are deterministic (`tg-<hash8>-<generation>`) so a crash between session creation and mapping write adopts the persisted session on the next message instead of orphaning it.
- **Routing** keys on `chat.id + message_thread_id`; the absent thread id (General topic or private chat) is its own mapping and posts omit `message_thread_id`. The five commands (`/status`, `/folder`, `/reset`, `/cancel`, `/help`) register on the harness command runtime, so every frontend discovers them and every execution logs `command/run`/`command/done`. Followups rely on the harness inbox queue with a per-topic cap (`queueCap`, default 3); beyond it the bot answers busy.
- **Workspaces** are a plugin-side read fence: every selection must be absolute, canonicalize through `fs.realpath` (the workspace registry's canon), and land inside a configured root by canonical-path containment. The harness sandbox remains the write fence under the same session cwd. Resume enforces cwd immutability: a persisted header whose canonical cwd differs from the mapped workspace surfaces a precise refusal and never replaces the session (the web gateway's `SessionCwdConflict` stance).
- **Transport** is a zero-dependency `fetch` client (`HttpTelegramApi`) behind a `TelegramApi` interface that tests fake. It implements the nine endpoints the plugin needs, per-operation token resolution through `ctx.credentials`, bounded retries on 429/5xx, global send pacing, and 4096-character HTML chunking with fenced code mapped to `<pre>`. Assistant output renders only from committed `assistant/message` events; one throttled status placeholder per topic shows tool activity and turn endings become one-line outcomes. Approvals and `ask_user_question` items are inline-keyboard buttons; unanswered prompts settle fail-closed at `approvalTimeoutMs`.
- **`@deepseek-ai/dsh-telegram-bundle`** (`packages/bundle/telegram-bundle`) is a patch-only bundle over `dsh-base` inserting the storage trio, the workspace registry, and the `telegram` row, whose deployment values ride environment seams (`DSH_TELEGRAM_*`), plus a shipped `telegram` profile template (`dsh --profile telegram`). The directory is named `telegram-bundle` because the `dsh-*` tsconfig-paths wildcard over `packages/bundle/*` would otherwise resolve `@deepseek-ai/dsh-telegram` to the bundle's `export {}` module.
- **`examples/telegram-agent`** is a runnable standalone leaf (sandboxed bash, fs tools, JSONL persistence, DeepSeek adapter, the plugin) with a keyless real-Loader smoke (`tests/keyless-smoke.e2e.ts`): the real composition boots against an in-process mock Bot API server and a scripted model, drives one topic message through the real HTTP client, and asserts the committed answer before a clean exit.

The plugin also registers the `telegram` settings namespace (`installSettingsSection` with the plugin `Config` as the section schema, base = the composition entry minus the runtime-only `transport`), and the runtime resolves every operation from the committed section instead of the entry: the authorization gate rebuilds synchronously on commit, the workspace guard and default-workspace resolution invalidate and rebuild lazily on the next admission, and pacing, queue, timeout, token-reference, and agent-route reads go through a live thunk. The web GUI's Plugins → Plugin configuration page renders a Telegram card over that namespace (shipped in `dsh-client-ui-settings-plugins` beside the bash/agent-loop/web-search cards, ten scalar fields with comma-list converters for the allowlists and roots); the card stays invisible in deployments that do not mount the plugin because the tab intersects served namespaces with registered cards. `apiBase` applies at the next plugin restart and `agentOptions` stays composition-owned.

The package test suite covers the formatting/chunking helpers, the authz gate, the workspace guard (traversal, symlink, containment), the mapping domain, and a full harness over real loop/persistence/storage services: creation, topic isolation, queue cap, commands, reset generations, restart resume, deterministic adoption, cwd-conflict refusal, approvals and questions through buttons, photo/document ingestion, closed-topic pause/resume, disposal of every registration, and the settings section (registration, committed overrides for queue cap, allowlists, roots, default workspace, approval timeout, and the token reference, plus the live-read defaults).

## Alternatives considered

- **A maintained Telegram SDK (grammY or telegraf)**: rejected — the needed wire surface is nine endpoints plus pacing and retries, which the `fetch` client owns directly; a dependency would add a versioned surface without deleting meaningful owned code, matching the LLM adapter's bare-fetch precedent. Revisit if webhook delivery, bot-command metadata sync, or payments ever enter scope.
- **Webhook delivery via `ctx.webServer`**: rejected for v1 — long-poll needs no host/bind assumptions and no secret-token handling; the Bot API contract is identical to the client.
- **Store the mapping in the session log or a private database**: rejected — the mapping is plugin-owned routing state, not model-visible session history; the storage domain is the same facility the workspace registry persists with, and the session-persistence SQLite handle is backend-private.
- **Reject concurrent messages per topic (the ACP stance)**: rejected — the harness inbox is durable and order-preserving, so queue-with-cap reuses tested machinery; ACP rejects because its wire protocol needs one prompt slot.
- **One table with an `archived` flag instead of a history table**: rejected — `/reset` must keep the retired session id for audit, and one row per topic key cannot hold both generations without synthetic keys; a second table keeps the current mapping key intact.

## Consequences

- Zero harness-core or existing-bundle changes; a deployment mounts the bundle, supplies an allowlist side and workspace roots (the plugin fails load otherwise), and the bot runs. The plugin restart/harness-restart path is plain resume.
- The `telegram` profile template and the bundle dependency land in the shipped CLI surface (`apps/cli`, `PROFILE_TEMPLATES`).
- Update replay dedupes in memory only (a bounded window), so a very long outage can redeliver an update as a new turn; durable dedupe would need its own storage unit and is deferred.
- Configuration now has two planes: the composition entry (load-time, validated, includes provider/model and the transport override) and the settings section (live, card-edited; `apiBase` still applies at restart). The section base strips the runtime-only `transport` because settings describe/schema resolution must never carry a live object.
- Posting into a closed topic fails with a 400 and pauses that topic until `forum_topic_reopened`; there is no delete notification, so dormant topics keep their sessions and mapping until a send fails.
- The mapping domain name is `telegram_topics` (underscored) wherever the earlier analysis wrote `telegram-topics`; the storage unit name pattern decides this, not the analysis.
